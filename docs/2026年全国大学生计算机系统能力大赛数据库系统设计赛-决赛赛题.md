# 2026年全国大学生计算机系统能力大赛-数据库管理系统设计赛-全国总决赛 · 性能测评说明

## 总则

本说明拟由赛项组委会发布，用于规定决赛测评中性能测试的组织方式、评分规则、数据与负载规格，以及正确性与持久性要求。

### 术语和定义

| 术语 | 规范含义 |
| --- | --- |
| 测评系统 | 组织并执行编译、功能测试、性能测量、恢复测试和结果生成的官方系统；具体执行组件称为“测评程序” |
| 必通过项 | 影响成绩有效性的强制要求；任一必通过项未通过时，不形成有效性能成绩 |

### 基本规定

本说明是参赛数据库必须遵守的规范，不是对当前自动测试覆盖率的完整描述。规范可以严于自动测试已经覆盖的范围；自动测试未检出某项违规，不构成可以违反本说明的依据。组委会有权依据测评日志、进程观测、参赛提交包源码及复核证据，对疑似违规情形进行判定；一经确认，相关成绩无效。

文档中的要求按下列四类标注或解释。后续重要条款在首次出现时标明所属类别；未单独标注时，以所在章节标题中的“强制 / 必通过 / 建议”等用语为准。类别冲突时，规范要求与审查性红线优先于优化建议；自动门禁是规范要求的可自动执行子集，不缩小 规范要求的适用范围。

| 类别 | 含义 |
| --- | --- |
| 规范要求 | 无论当前自动测试是否覆盖，参赛实现均须遵守 |
| 自动门禁 | 当前测评程序会直接检查；失败时自动终止或该次性能成绩计 0 分 |
| 审查性红线 | 自动测试可能无法穷尽，但一经日志、源码或复核证据确认，即判定为违规或成绩无效 |
| 优化建议 | 只影响性能和排名；不单独构成正确性失败，也不得被解释为允许降低 ACID 或本说明其他强制语义 |

1. 决赛性能测试采用 TPC-C 5.11 兼容饱和负载；排行榜指标为 NewOrder 成功提交速率，单位为“笔/分钟”，报告字段为 NewOrder/min。
2. 功能正确性校验、COMMIT 持久化校验或崩溃恢复测试未通过时，不进入性能评分，该次参赛提交包的性能得分为 0。
3. 测评生成的 SQL、答案、随机种子、运行时标识符、隐藏校验项、原始比较值、完整日志和未失败用例不向参赛队伍公开。发生失败时，学生报告仅展示脱敏后的阶段、失败类别、可公开的序号或进度，以及测评程序已经确认的观察事实；完整证据由组委会留存复核。
4. 【规范要求 / 审查性红线】为保证公平性，参赛项目的编译命令与 rmdb 服务以专用非特权身份运行；测试客户端、在线 SQL/答案、性能负载和类型化结果由测评程序独立管理。参赛提交包中的代码不得修改、替换、探测或依赖测评资产与其内部实现细节；一经测评或复核确认完整性破坏，该次测评无效。
5. 【规范要求】正式性能库使用不透明的库名、表名、列名和 CSV 文件名，并按测评程序确定的非固定顺序建表、建索引、装载和校验。标识符替换用于检验实现的通用性，不构成保密边界；数据库实现必须按收到的 SQL 正常解析和执行，不得依赖公开 TPC-C 标识符，不得依赖固定客户端数、固定连接模式或固定请求交错作为正确性前提。
6. 【规范要求】数据库结果统一使用公开的 RMDB Wire Protocol。功能、恢复、 装载和大查询保留 EXEC_STREAM 的 META/类型化 ROW/唯一终结 frame；排名事务在每个 连接开始计时前使用 PREPARE_SET 安装语句与 schema 字典，并以 EXEC_BATCH 执行 依赖阶段。测评不读取 output.txt，也不发送 SET OUTPUT_FILE OFF/ON。排名前会执行本说明列出的语义预检；任一预检失败均不进入计时阶段。预检通过仅表示所列预检项未失败，不构成对实现符合本说明全部条款的证明，也不减免其他规范要求与审查性红线。
7. 每次服务启动和崩溃后重启都必须通过 SQL 测活：服务端口须由预期 rmdb 进程树监听，并通过 Wire Protocol 成功执行精确语句 show tables;，返回完整的 COMMAND_OK 或 META ... RESULT_END。仅能建立 TCP 连接不算就绪；空库返回 0 行 是有效结果。

正式测评由组委会测评系统统一驱动，不另行发布可独立执行的性能客户端。参赛队伍应 使用自己的 SQL 和事务回归工具验证实现，不得依赖或探测测评程序内部的标识符映射与随机流。参赛数据库端网络协议的完整字节规范见附件 A《RMDB Wire Protocol》。

## 二、测评流程与成绩形成规则

### （一）总体流程

完整自动测评按下列顺序执行：

```text
编译与服务启动
↓
功能正确性测试
├─ 通过   → COMMIT 持久化校验
└─ 未通过 → 跳过 COMMIT 持久化校验
↓
崩溃恢复相关测试（无论上述结果如何均执行，用于补充诊断）
↓
汇总功能正确性 / COMMIT 持久化 / 崩溃恢复测试结果
├─ 任一未通过 → 不进入性能评分，得分为 0
└─ 全部通过
↓
性能测试
├─ 生成并装载正式规格数据，完成装载校验
├─ 预热 30 秒（不计入排名）
├─ 连续执行 3×150 秒正式测量
├─ 全部测量结束后执行在线一致性校验
├─ 计算三个窗口 NewOrder 成功提交速率的中位数，作为排行榜取值
├─ 非正常终止数据库进程（保留数据目录）
├─ 在 90 秒就绪预算内重新启动数据库并完成崩溃恢复
└─ 执行恢复后一致性与持久性校验
↓
读写诊断（仅当前述必通过项全部通过）
├─ 复用恢复后的性能测试库
├─ 10 秒诊断预热（不采集）
├─ 通过 strace 观察 60 秒同规格 TPC-C 混合负载
└─ 展示事务、进程 I/O、系统调用与调用总数的聚合信息
↓
清理环境并结束测评
```

### （二）成绩与排名

| 项目 | 规则 |
| --- | --- |
| 得分（Score） | 全部必通过项通过后记 100 分；任一必通过项未通过时记 0 分 |
| 排名性能指标 | 仅在性能成绩有效时计算：三个窗口 NewOrder 成功提交速率的中位数；数值越大表示吞吐量越高，排行榜以 NewOrder/min 列展示该值 |
| 排名规则 | 按三个正式测量窗口的 NewOrder/min 中位数从高到低排序 |
| 有效性前提 | 事务混合比例、计数一致性、客户端规模、数据规格、在线一致性及崩溃后校验均须满足测评系统要求 |

说明： 功能正确性校验未通过时，跳过 COMMIT 持久化校验和性能阶段，但崩溃恢复测试仍会执行；恢复结果用于补充诊断，不会改变已判定为未通过的必通过项。排名负载仅有一次 30 秒预热，该阶段事务不计入排名。在线一致性校验在三个正式测量窗口全部结束之后、强制终止测试之前执行。恢复后校验用于确认成功提交结果在进程被强制终止后仍完整、正确。该次 排名后重启的就绪预算为 90 秒；性能阶段之前的崩溃恢复用例仍保持 60 秒重启预算。

读写诊断是全部必通过项通过后的附加观测阶段。该阶段发生采集失败或诊断负载 异常时，报告标记为 WARN，已经形成的 Score 和排行榜结果保持不变；该阶段不属于成绩 必通过项。

排名测量期间，报告还会给出 RMDB 的 CPU 占用（平均/峰值，以单核为 100% 计； 多线程或多进程实现可超过 100%）以及相对主机的占用比例。峰值内存与磁盘占用会 写入排行榜附属列 max-rss(GB)、disk-usage(GB)。上述资源指标仅供分析与对照， 不参与主排序。

### （三）学生可见反馈与信息边界

测评平台向参赛队伍展示判定、得分、排行榜指标和分阶段报告。未通过项会给出 Failure category、Failed substage 和脱敏后的 Key fields；在能够安全公开时，还会给出操作类型、超时边界、表序号、语句序号、完成进度及已确认的观察事实。这些字段用于区分编译、进程、传输、协议、SQL、超时和语义失败，不用于公开测试数据。

协议失败会额外公开固定的 Protocol constraint 文本，例如未知 frametag、非零 flags/reserved、META/ROW 顺序、row_count 或 PREPARE/BATCH 结构不符；这些文本只描述 公开字节契约，不回显实际 tag 数值、响应内容或服务端诊断。

学生可见反馈不包含测评生成的 SQL 或答案、运行时表名和列名、测评内部路径或生成数据文件路径、随机种子、隐藏校验标识、完整服务日志或逐条系统调用 trace。一致性比较是例外：报告会公开允许列表内的检查名、该次运行的期望值、实际值与 tolerance；严格 FLOAT32 检查以 0x???????? bit pattern 和 0 ULP 展示。它们不携带 SQL、运行时标识或记录键。组委会保留完整证据用于赛后复核和申诉处理。

## 三、性能测试规格

### （一）负载特征

1. 系统在高并发条件下持续接收事务，采用 TPC-C 饱和负载；客户端不设置事务间思考时间，并持续发送请求以维持系统负载。
2. 正式配置使用 32 个客户端和 160 槽确定性轮盘。由隐藏 workload seed 派生 4 个热点仓库；每个热点仓库占 26 槽，其余 46 个仓库各至少占 1 槽，另有 10 个冷仓 在每个阶段各增加 1 槽。槽内容按阶段独立洗牌，热点仓库身份在整次测评中保持不变。 客户端按 5 波覆盖 160 槽的映射推进，不使用固定终端仓库。 slot_index(client_id, txn_no) = (client_id + 32 × (txn_no mod 5) +13 × floor(txn_no / 5)) mod 160 client_id 从 0 到 31，txn_no 在每个阶段从 0 开始，并在选出一笔事务参数时递增； 最终放弃的事务也占用该序号，重试不增加序号。任意同步的连续 5 波覆盖全部 160 槽， 13 与 160 互素，使后续轮转不会固定在同一槽组。
3. 热点仓库约承载 65% 的归属流量；热点仓库内 65% 的事务进入该仓库由 seed 派生的 单一热点 district。NewOrder 每条明细有 25% 从 24 个 seed 派生热点商品中均匀选取， 有 8%选择非本仓的远程供货仓；Payment 有 30% 选择非本仓的远程客户仓。 热点仓库、热点 district、热点商品及阶段轮盘使用与事务参数随机流隔离的路由随机域。
4. 【规范要求】参赛实现须在本说明规定的多客户端并发负载下正确处理跨事务冲突，包括 同一分区的 d_next_o_id、热点 stock 记录和 Delivery 领取未配送订单等；不得仅 优化 NewOrder 而忽略其余事务的正确执行与成功提交。隔离语义、原子性、可见性与冲突处理必须以真实并发执行为前提成立，不得以“单线程假设”“固定客户端数假设”或“请求不会交错”作为正确性前提。

【优化建议】锁粒度本身（例如偏粗的锁）不单独构成正确性失败，但通常会显著降低 吞吐与排名。

【规范要求 / 审查性红线】若实现通过取消必要冲突检测、共享跨事务可变状态、或使未提交更新对其它事务可见等方式换取吞吐，一经测评或复核确认，按正确性失败或成绩无效处理；不得将“允许粗粒度锁”解释为允许降低隔离语义或省略并发正确性。

5. 每份参赛提交包使用独立生成的数据与访问序列；规模、分布、事务比例和测量时长保持相同。具体随机值不公开，参赛程序不得依赖某个公开常量、固定订单号或预先推断的 访问序列。
6. 可重试冲突路径复用首次生成的归属仓库、district、商品、供货仓、远程客户目标和客户选取方式；重试不会重新抽取参数，也不会借换仓改变覆盖统计。

### （二）Wire Protocol 排名传输

协议保留两个互补路径：

- EXEC_STREAM 面向任意 SQL 与大结果，查询继续逐个 META → ROW* → RESULT_END 流式发送；功能、恢复、建表、装载和一致性查询均可复用这条路径。
- PREPARE_SET + EXEC_BATCH 面向排名高频执行路径。每个连接只准备一次不透明 SQL 模板、 parameter type 和 query schema；后续 batch 只发送 statementid 与 typed value，成功 响应只携带查询行，不重复 SQL、schema 或逐条 DML ACK。

同一连接仍只有一个 outstanding request，协议不要求 pipeline、requestid 或乱序响应。 EXEC_BATCH 内 operation 必须严格顺序执行；客户端只在必须读取前一阶段查询值才能 生成后续参数时增加一次 batch 边界。五类事务的批次边界、无冲突往返数及混合负载 推导见附件 A 第 7 节。

PREPARE_OK 中每个 query 的列数、顺序和类型必须与实际 SQL 投影一致；测评程序会按排名模板逐列核对类型，不能以单个占位列替代未被驱动读取的投影列。NewOrder 的无效 商品路径会在第二个 batch 中写入此前有效明细后执行 ABORT，用于确定性校验 prepared 执行路径对订单、索引、库存和明细的完整回滚。

所有排名 batch 都设置 AUTO_ABORT。任一 operation 失败时，服务器须先回滚并结束 活动事务，再返回失败 BATCH_RESULT；失败 batch 不返回任何部分查询结果。可重试冲突 使用 TRANSACTION_ABORT 状态，客户端直接重试且不会再发第二次 ABORT。完整 header、 payload、状态码、边界和失败计数要求见附件 A《RMDB Wire Protocol》。

以下内容仅供实现和性能优化参考，不构成额外评测要求：

- 连接对象可持有 statement_id → parsed statement/plan + parameter types + result schema； PREPARE_SET 验证全部模板后原子替换字典；EXEC_BATCH 从有界 payload 中顺序解码，并将小查询结果写入有界 response builder。typed CHAR 参数宜直接绑定到 AST 或执行计划槽位，避免未经转义地拼回 SQL。
- 高负载路径可按连接复用 1 MiB 以内的 request/response buffer；多个连接可按 SQL fingerprint 共享只读 parsed plan，但须隔离连接内 statementid 和事务状态。整个 batch 可一次构造并聚合写出 BATCH_RESULT，所有 buffer、结果行数和排队任务都应设置硬上界， 并对慢连接实施背压。

### （四）事务类型与语义要求

| 事务 | 基本语义要求 |
| --- | --- |
| NewOrder | 正确分配订单号；写入 orders、new_orders 及全部 order_line；更新 stock；任一明细失败时整笔事务回滚 |
| Payment | 更新 warehouse、district、customer，并插入 history；按姓名检索客户时遵循中位选取规则 |
| OrderStatus | 定位客户最近一笔订单，读取其订单头（含 o_entry_d、o_carrier_id，按 TPC-C 2.6.2.2）与全部明细；o_entry_d 须非空回读，o_carrier_id 须在 0～10 内 |
| Delivery | 对仓库内各非空分区处理最早未配送订单；空队列分区跳过；以该订单全部 ol_amount 的 SUM 增加客户余额，并同步更新 new_orders、orders、order_line 与 customer |
| StockLevel | 对最近 20 笔相关订单，统计库存低于阈值的不重复商品种类数 |

补充要求：

1. NewOrder 中设置的无效商品号属于业务预期回滚路径；回滚后不得残留任何部分订单记录或相关索引项。
2. Stock 更新须采用与并发安全相符的相对更新方式，禁止以未正确保护的读改写造成丢失更新。测评客户端会先按 (supply_warehouse, item_id) 升序、去重后锁定本笔 NewOrder 的全部库存行，再按原始明细顺序读取和更新，以避免热点商品的反向锁序形成环。
3. Delivery 须按“最早未配送”语义领取订单，不得任意选取；某分区没有未配送订单时，该分区应被安全跳过，而不是把整笔 Delivery 判为失败。
4. OrderStatus 的“最近订单”与 Payment 的“中位客户”依赖稳定、正确的排序语义。
5. StockLevel 必须按商品标识去重，结果须与本说明给出的 COUNT(DISTINCT …)语义一致。测评客户端固定发送单条 COUNT(DISTINCT …)

查询，不提供客户端拆分查询、客户端去重或其它兼容路径。数据库可在内部选用索引探测、嵌套循环、哈希聚合等物理计划，但： （1）不得改变该 SQL 的对外语义；

（2）不得将去重或计数义务转移到客户端； （3）不得依赖“客户端会再次校正结果”的假设；

（4）必须在规定时限内返回正确的类型化结果。

三个 150 秒正式测量轮会逐轮校验五类事务的计数一致性，并要求每类事务在测量窗口内至少成功提交一笔，并要求至少一笔 Delivery 实际处理排队订单；仅提交始终没有处理任何 记录的空 Delivery 不能满足事务族完成门禁。业务预期回滚仅用于验证 NewOrder 回滚路径， 不计入 NewOrder 成功提交数或排行榜统计；数据库异常中止、协议失败、超时和放弃不得计为 业务预期回滚。报告中的 abort-rate 等列供诊断参考，成绩有效性以本节所列计数一致性与 最低成功提交要求为准。

仓库覆盖要求按测量窗口内的完成事务样本量缩放。单轮达到 400 笔完成事务后，要求至少 45/50 个归属仓库出现完成事务且 4 个热点仓库全部出现完成事务；三轮合并达到 400 笔后， 要求覆盖全部 50 个仓库且覆盖全部热点仓。低于 400 笔时，最低覆盖仓库数按 ceil(完整要求 × 完成数 / 400)计算，不强制“全部热点仓”条件。完成事务包括成功提交和业务预期回滚，不包括放弃、截止停止或测量窗口后的 grace-tail 完成。学生报告公开每轮及合并覆盖仓库数，完整 50 仓直方图和热点比例仅保留在后台日志中。

### （五）可配置隔离级别（决赛功能门禁）

决赛功能测评要求实现以下两条会话级配置语句：

```text
SET TRANSACTION ISOLATION LEVEL SNAPSHOT ISOLATION;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

设置成功后应持续作用于该连接后续新开启的事务；测评会在连接建立后、首个 BEGIN 前设置一次，不会在活动事务中重新设置。除配置语法测试外，同一语义测试点中的多个连接只使用同一种隔离级别。

【自动门禁 / 规范要求】功能侧由配置、SI、SER 三个模型分组执行历史：含 3 个单会话 配置历史、18 个 SI 多会话历史和 27 个 SER 多会话历史，共 48 个独立历史。 SI 按事务级 MVCC 快照、本事务写入可见性、提交/回滚及同一逻辑记录写写冲突判定；SER 在 SI 基础上检查记录读、谓词读、空结果范围读和读写反依赖。

除 SERIALIZABLE 隔离语义外，本赛题额外规定以下确定性冲突响应契约（赛题额外协议，严于“任意正确的可串行化实现均可在 COMMIT 时再裁决 victim”的通用表述）：若当前 SELECT、INSERT、UPDATE 或 DELETE 新增 rw 反依赖，并形成本赛题 SSI 场景所定义的危险结构（包括但不限于 record/predicate 写偏序及题面规定的多事务危险依赖组合），则必须由当前语句立即返回 TRANSACTION_ABORT 并回滚当前事务。不接受将此类冲突 推迟到 COMMIT 再报告，也不接受改选其他 victim。实现不得以“结果仍可串行化”或“可在提交阶段统一裁决”为由降低上述即时中止义务。

TPC-C 排名连接固定使用 SNAPSHOT ISOLATION，并在安装 PREPARE_SET 字典前完成设置。

### （六）StockLevel 去重语义（决赛新增）

决赛功能测试要求数据库引擎支持 COUNT(DISTINCT …)；StockLevel 须对低库存商品按种类 去重后计数。

参赛数据库必须原生支持 COUNT(DISTINCT …)，包括与多表连接和过滤条件组合使用。解析器须同时兼容标准写法 COUNT(DISTINCT col) 和带额外括号的 COUNT(DISTINCT(col))，两种写法的语义相同。功能侧 Distinct 用例还会校验订单窗口 过滤、库存阈值比较（s_quantity <

threshold，等于阈值不得计入）、多仓隔离以及 join 扇出下的去重。

【自动门禁】排名负载启动时会实际探测该语义；探测失败即停止排名测量。正式排名与最后的 非计分 I/O 诊断均复用同一套原生服务端事务实现，不存在客户端去重或拆分查询的兼容路径。

【规范要求】对外结果必须与下列查询语义一致；测评客户端固定发送单条 COUNT(DISTINCT …)。内部物理计划可自选，但不得弱化 DISTINCT、过滤、连接或仓库隔离 语义，也不得依赖客户端侧后处理。

逻辑结果应与下列查询等价（书写形式可不同，语义须一致；实际语句由测评程序生成）：

```sql
SELECT COUNT(DISTINCT s_i_id)
FROM order_line, stock
WHERE ol_w_id = :w_id
AND ol_d_id = :d_id
AND ol_o_id < :next_o_id
AND ol_o_id >= :next_o_id - 20
AND s_w_id = :w_id
AND s_i_id = ol_i_id
AND s_quantity < :threshold;
```

参赛队伍须保证事务结果正确、在并发下语义成立，并维护事务原子性。

决赛功能测试还会对 SQL FLOAT 执行 TPC-C 金额计算校验：连续相对加减、 多行 SUM、大金额叠加小金额、事务提交与回滚后的值均须正确。Wire Protocol 直接传输 IEEE-754 binary32 bit pattern，不再比较六位小数文本格式。排名 NewOrder 的价格乘 数量由测评程序计算后作为 prepared FLOAT32 参数绑定；不要求数据库额外支持投影表达式中 的浮点乘除。功能侧仍可能发送带十进制 FLOAT literal 的普通 EXEC_STREAM SQL。

正式测评采用以下公开且唯一的 FLOAT 规则：

1. FLOAT 列、FLOAT literal 和 prepared FLOAT32 参数均先转换为 IEEE-754 binary32， 舍入模式为 round-to-nearest, ties-to-even；+0 与 -0 比较时视为同一数值；
2. FLOAT 相对加减在每次 SQL 更新处执行一次 binary32 加/减并舍入。Payment 与 Delivery 会读取更新前后值，按该规则逐笔比较，tolerance 为 0 ULP； Payment 逐笔检查失败时，学生报告会直接给出 Before、Bound FLOAT32 amount、 Expected、Actual 和 Tolerance；前四项同时显示十进制值与 0x???????? binary32 原始位模式。该检查针对单次相对更新而非全表聚合。在 SNAPSHOT ISOLATION 下，若更新所依据的行版本已经过期，必须返回 TRANSACTION_ABORT，不得把该更新应用到更新后的行版本；
3. SUM(FLOAT) 将每个已存储的 binary32 输入精确扩展为 binary64，在 binary64 中 累加，最后只舍入一次为 binary32；结果通过 Wire Protocol 以 FLOAT32 返回；
4. 所有受检 FLOAT 值必须有限，NaN 和正负无穷均直接失败。单笔事务内可由输入精确 推导的 order_line、history 写入值与 stock 相对更新按 bit pattern 比较， tolerance 为 0 ULP，不使用按金额规模或操作次数放大的误差带；跨排名量级行集的 全表 SUM 按下一条单独规定。
5. 第 3 条规定了 SUM(FLOAT) 的语义，但数据库自行决定 binary64 的累加顺序，本规范不对其作出规定。因此对行数达到排名量级的两项账本可推导聚合 （全表 SUM(h_amount)、新订单 SUM(ol_amount)），测评程序按边界感知方式判定： 先算出精确和 S 与该规模下任意累加顺序的误差上界 epsilon = n * 2^-53 * S（n 为加数个数， 全部为非负数），再接受区间 [S-epsilon, S+epsilon] 舍入所得的 binary32 值。由于 epsilon 远小于 半个 ULP，只有当 S 恰好落在 binary32 舍入边界的 epsilon 邻域内（即任何累加顺序都无法区分的情形）才会同时接受相邻值；其余情况仍是逐位判定。单笔事务内的相对加减、 单个订单的 SUM(ol_amount)（明细不超过 15 行）以及整数量累计 SUM(s_ytd) 不属于 此列，一律 0 ULP。

Delivery 读取订单明细后，测评账本直接按每个 ol_amount 的实际 binary32 位值形成 精确 binary64 SUM 输入，不把该值先四舍五入为整数分、再由整数分重建 FLOAT32。 测评客户端同时执行 SUM(ol_amount)，将其与逐行位值复算结果按 0 ULP 核对，并把该 SUM 的 FLOAT32 结果原样绑定到 c_balance = c_balance + ol_total。整数分解析只用于 金额范围、业务输入和遥测，不参与 ol_total 的构造。

## 四、排名指标与成绩有效性

### （一）排名指标定义

每一正式测量窗口内：

```text
NewOrder 成功提交速率（笔/分钟）
= 该窗口内成功提交的 NewOrder 事务数 ÷ 窗口时长（秒） × 60
```

默认窗口时长为 150 秒。排行榜取三个窗口上述指标的中位数，在 NewOrder/min 列显示，并按该值从高到低排名。

排行榜的 rank 对象还附带诊断列：abort-rate、p99-ms、p50-ms、 max-rss(GB)、disk-usage(GB)。参赛队伍报告详情中的 TPC-CCPU 平均值和峰值仅作运行时资源参考，不进入排序字段。

### （二）成绩无效的常见情形

出现下列情形之一时，性能成绩通常记为无效（0 分），包括但不限于：

1. 事务计数一致性校验失败，或某一正式测量轮中某类事务未能至少成功提交一笔；
2. 客户端数量或数据规模不符合测评配置（正式测评为 32 连接、正式数据规格）；
3. 在线一致性校验未通过；
4. 进程被强制终止后，成功提交数据丢失或恢复结果错误；
5. 延迟与成功提交等统计结果明显不一致，无法通过测评系统校验。

禁止以截断、伪造或错序 Wire Protocol frame 等方式规避校验。测评系统将对 schema、类型、行数、事务计数与数据库状态进行交叉核对。

### （三）延迟指标说明

报告中的 NewOrder 延迟指客户端发起到确认提交成功的端到端时延，仅统计成功提交的事务。合并各正式测量窗口样本后给出 p50、p99 等分位数；若样本池经蓄水池等方式截断，则相关分位数为近似值。吞吐提高而 p99 显著恶化时，通常表明锁等待、日志刷盘、缓冲池或长查询等路径存在瓶颈。

## 五、正确性与持久性校验规则

### （一）数据装载

初始 order_line 行数和总行数不在不同参赛提交包之间保持固定。测评程序记录本次运行的 精确 order_line 行数，装载校验与一致性校验均使用该精确值。固定关系共 10,050,550 行，总行数为 10,050,550 + 本次运行的

order_line。装载结果须持久化；orders.o_ol_cnt 须与对应明细行数一致；仓库、区、订单号等关联列取值范围须正确。

| 项目 | 默认值 | 说明 |
| --- | --- | --- |
| 装载阶段 SQL 总预算 | 900 秒 | 自连库成功起，覆盖建表、建索引、LOA D、COUNT、完整性与内容抽样的整段 SQL 校验 |

测评执行器可在 SQL 总预算之外保留少量进程收尾与结果传输时间；这不扩大数据库执行 SQL 的 900 秒预算。参赛提交包不能修改正式时长配置。

测评程序在密封 rmdb 就绪后，按下列固定顺序执行（表名、列名和 CSV 文件名采用不透明标识符，表顺序由测评程序确定；本文所列逻辑名称用于定义规范语义）：

```sql
连接 rmdb（Wire Protocol）
→ CREATE TABLE × 9
→ CREATE INDEX × 10
→ LOAD CSV × 9
→ COUNT(*) × 9（精确行数）
→ 初始状态完整性校验
→ 索引键跨表关系抽样
→ 跨分区内容抽样
→ 通过后进入排名预热/测量
```

（1）建表（CREATE TABLE × 9）

测评程序依次发送 9 条 CREATE TABLE 语句。字段、顺序、类型及初始行数以第三章第（三）节的完整逻辑数据模式为准；运行时不透明标识符与该逻辑模式一一对应。

（2）建索引（CREATE INDEX × 10）

测评程序依次发送第三章第（三）节规定的 10 条 CREATE INDEX 语句。运行时可替换表名和列名，但索引数量、所属逻辑表、键列及键列顺序保持不变。

（3）装载（LOAD × 9）

对每张表发送 load <csv路径> into <改写表名>;，路径与文件名由测评程序生成。实现须支持大表流式装载；order_line 与 stock 数据量最大，装载超时通常发生于这两张表。

（4）行数校验（COUNT × 9）

对每张表执行 SELECT COUNT(*) …，必须与测评程序记录的精确行数一致 （含本次运行动态生成的 order_line）。任一张不符即失败，类别为 LOAD row-count mismatch。

（5）装载后完整性与关系校验

下列校验在全部 COUNT 通过后执行。系统不执行大表全量外键 join，而是核对初始状态聚合不变量，并从本次数据中选择分散的索引键进行跨表关系抽样。抽样覆盖 district→warehouse、customer→district、orders→customer、new_orders→orders、 order_line→orders/item/stock 以及 history→customer。具体抽样键和比较值不公开。公开的判定语义包括：

| 校验语义（逻辑列名） | 判定要求 |
| --- | --- |
| orders 表的 SUM(o_ol_cnt)stock.s_quantity orders.o_ol_cnt | 等于 order_line 行数全部位于 10～100 范围内全部位于 5～15 范围内 |
| orders.o_carrier_id=0 的行数 | 等于 new_orders 行数 |
| 初始未配送明细数量 | 与本次生成数据一致 |
| stock.s_ytd/s_order_cnt/s_remote_cnt | 初始值均为 0 |

（6）内容抽样校验

测评程序使用本次生成数据的真实值核对装载内容，而不只核对行数。抽样覆盖商品价格、初始未配送明细金额的 FLOAT32 位值、库存数量、仓库和分区初始值、客户状态、订单状态及明细数量，并分布在多个仓库与分区。性能预检还会对固定初始未配送订单逐行核对金额 位值及 SUM，避免仅以数据库现存错误值建立自引用账本。具体抽样键、运行时标识符和 比较值不向参赛队伍公开。

装载阶段的 SQL 发生失败或超时时，报告在参赛队伍可见摘要的 Key fields 中写入以下归因字段：

| 字段 | 含义 |
| --- | --- |
| Load step | 脱敏后的装载子步骤，例如 CSV loading (table ordinal 7)、row-count validation (table ordinal 3)、integrity validation、content validation、table creation / index creation |
| Table ordinal | 打乱装载顺序中的表序号（1–9）；不是逻辑表名 |
| Operation | 如 data loading / row-count validation / integrity validation |
| SQL failure / Timeout boundary / Transport event | 依失败族出现：显式 ERROR、响应读超时、连接重置等 |

学生报告不展示原始 SQL、运行时表名、文件路径或原始比较值；这些信息仅由组委会留存 用于复核。

类别示例（与报告 Failure category 一致）：

- Worker watchdog timeout / SQL timeout / Response read timeout / Stage timeout：预算内未完成
- LOAD row-count mismatch：某一序号对应表的 COUNT 结果不符
- LOAD integrity mismatch / LOAD content mismatch：完整性或抽样值错误
- Client/server transport failure：连接在完整终结前关闭、重置或 EOF
- Server ERROR response：服务端返回完整、合法的 ERROR 终结（或 BATCH_RESULT status=ERROR）

### （二）在线一致性

三个正式测量窗口全部结束之后，强制终止前执行固定 6 项整数 + 7 项 FLOAT32 快速检查：整数部分只访问小表或索引键；FLOAT32 部分采集七个聚合的崩溃前 bit pattern，并将其中可由账本推导的 history、stock、新订单 order_line 聚合与账本核对—— 其中 stock 为整数量累计，按 0 ULP 判定；history 与新订单 order_line 行数达到 排名量级，按上文 FLOAT 规则第 5 条的边界感知方式判定。完整校验在重启后 执行，包含 37 项整数聚合校验和 7 项金额聚合校验，包括：

1. warehouse、district、customer、item、stock、orders、order_line、 history 和 new_orders 等关键表的行数与成功提交事务计数相符；
2. district 下一订单号、客户付款与配送次数、库存订单次数等聚合量与事务账本一致；
3. 仓库、分区、客户、订单明细、商品和库存等关键标识及数量仍在合法范围；
4. Payment、Delivery、NewOrder 的单次 FLOAT32 更新按公开 FLOAT 规则以 0 ULP 校验；Delivery 明细金额的账本贡献取自实际返回的 binary32 位值，不经过整数分重新 量化。崩溃前后七项金额聚合 bit pattern 分两档比对： 0 ULP 档（SUM(w_ytd)、SUM(d_ytd)、SUM(s_ytd)）：加数分别只有 50 行、 500 行且指数范围集中，或为精确小整数，任意累加顺序的 binary64 部分和都精确，因此结果唯一，逐位比对； ≤1 ULP 档（SUM(c_ytd_payment)、SUM(h_amount)、SUM(c_balance)、新订单 SUM(ol_amount)）：加数跨越的指数范围（c_balance 还存在正负抵消） 使 binary64 总和在 binary32 舍入粒度以下依赖累加顺序，而崩溃前后两次扫描的顺序不受本规范约束。丢失一笔已提交金额造成的偏移量级为数百至数万 ULP，仍会被该档检出；逐键持久性另由恢复后的抽样关系审计逐位保证。

强制终止前不执行大表完整扫描或逐行关系审计；这些检查只在恢复后执行一次。

### （三）崩溃后一致性与持久性

【规范要求】成功 COMMIT 所对应的事务效果，在进程被 SIGKILL 并重启后仍须正确可见；未成功提交的效果不得部分可见。该要求属于成绩有效性的强制语义，不因实现选用何种内部日志或同步机制而减免。

【规范要求 / 自动门禁】在满足上述持久语义的前提下，本赛题另规定下列可观测、可复核的自动审计兼容性契约。其目的是使测评程序能够对“COMMIT 成功应答前是否已完成稳定化”给出确定性判定。即使其他日志布局、force-at-commit 或同步机制在理论上可能具有等价持久性，无法产生本节规定的可核验证据时，仍判定为未满足本赛题契约，功能测试失败且不进入性能评分。不得以“理论等价但不可审计”主张免责。

COMMIT 持久化校验按以下规则判定：

- ACK 时序要求： COMMIT 成功应答前，对应 WAL commit record 必须已被同一 ACK 窗口内的稳定化操作覆盖。生产实现可以采用 group commit，但本校验负载按顺序发出 COMMIT；不得先返回多个成功 ACK，再补做一次与这些窗口错开的同步操作。
- 有效稳定化行为： 同一 ACK 窗口内，必须先在受支持的 WAL 存储对象上观察到 返回值大于 0 的新写入，再由作用于同一存储对象的可核验同步操作覆盖该写入。测评程序按打开文件对象而非单纯路径字符串关联写入和同步，因此同一 segment 经重命名、重新打开或交由其它线程刷盘后仍可正确识别。当前可核验机制包括 fsync、fdatasync、 O_SYNC/O_DSYNC、RWF_SYNC/RWF_DSYNC，以及发生 WAL 正字节写入后的 sync/syncfs。其中 syncfs 还要求：用于调用的文件描述符所对应的路径必须位于本次数据库目录之内；仅“作用于同一文件系统”但不落在本次数据库目录命名空间 内的 syncfs，不作为有效覆盖证据。
- 无效行为（不予计入）： 零字节写入、重复刷历史写入、仅写入操作系统页缓存、 等待 checkpoint 或正常关库后再刷盘、对非目标 WAL（包括其它数据、日志或临时 token 文件）执行写入或 fsync，以及单独调用 msync，均不能覆盖新的 COMMIT。
- WAL 日志文件命名要求（强制 / 赛题额外契约）： 兼容单文件<build>/<本次数据库名>/db.log；同时允许数据库根目录下具有非空后缀的 db.log.* 分片，以及 wal/子目录中的任意层级普通文件。segment 的真实路径必须留在本次数据库目录内；db.logger、其它同级日志、符号链接逃逸目标和数据库目录外文件均不属于 WAL 命名空间。
- 分片目录持久化： 审计开始后新建、链接或重命名 segment 时，在该 segment 首次 用于覆盖 COMMIT 前，还必须对受影响的父目录执行成功的 fsync；跨目录重命名须同步 源、目标父目录，新建 wal/层级须逐层同步父目录。sync 或路径位于本次数据库目录 内的 syncfs 可以等价覆盖这些目录项。审计开始前已存在的 segment 不追溯该项证据。
- 未适配机制： 若只观察到测评程序无法解码为 WAL 稳定化操作的 io_uring 活动，将判定为参赛数据库未满足本赛题自动审计兼容性契约，而不是测评环境异常。

测评系统通过非正常终止进程模拟故障，并在重启后校验：

1. 成功提交事务仍然可见且完整；
2. 未成功提交事务不得部分可见；
3. 恢复过程不得重复施加不应存在的修改；
4. 日志、数据页与元数据在恢复后保持一致；
5. 执行上述 37 项整数与 7 项金额聚合校验；七项 FLOAT32 聚合按第（二）节的两档 tolerance 与崩溃前捕获的 bit pattern 比对；核对账本保留的 NewOrder、Delivery、 库存、客户和 history 样本，并对全部 500 个 warehouse/district 分区逐一核对订单数、明细数、未配送队列、空配送时间行数、 o_carrier_id=0 行数及 d_next_o_id；
6. YTD 更新链完整性： w_ytd 与 d_ytd 是原地累加的 FLOAT32 单元，“初始值 +金额之和”的聚合本身无法证明没有丢失更新。因此测评程序会依据每笔已提交 Payment 在自身事务内读取的更新前值与更新后值，对每个实际发生 Payment 的仓库和分区验证完整更新链，并在恢复后核对最终值。该判定不依赖事务提交顺序或 FLOAT 聚合顺序；具体证据压缩方式仅由组委会留存，不属于学生可见契约。公开装载初值仍为 w_ytd = 300000、d_ytd =30000。

当前每个恢复用例执行一次经验证的 SIGKILL → 重启 → 类型化查询校验；不会在同一用例中再追加第二次重启。因此，“多次恢复结果稳定”属于建议参赛队伍自行执行的幂等性回归测试，不属于测评程序单个用例内的重复恢复必通过项。

COMMIT 持久化校验与崩溃恢复测试相互独立：前者验证成功响应前是否已完成规定的稳定化操作，后者验证日志恢复后的数据库语义。当前测评运行于普通容器目录，进程 SIGKILL 不等价于整机断电，因此同机重启不作为完整的电源故障模拟。

### （四）读写诊断报告（不计分）

全部必通过项通过后，测评程序复用已经完成崩溃恢复的性能数据库。数据库启动后， 先运行 10 秒 TPC-C 混合负载作为诊断预热；随后将 strace 附加到 rmdb 进程， 再运行 60 秒相同并发和事务混合比例的负载。该观测发生在三个正式排名窗口之外， 因此不会污染排行榜吞吐。

参赛队伍报告展示以下聚合信息，不公开逐条系统调用的原始 trace：

1. 诊断负载中五类事务的 Committed、Attempted 和 Commit rate；性能结果区另行 展示 attempted、committed、expected rollback、abandoned 与 completion；
2. /proc/<rmdbpid>/io 在观测区间内的 Bytes read、Bytes written、读写字符数、读写系统调用计数与取消写入字节数；
3. 次缺页、主缺页、自愿与非自愿上下文切换，以及用户态/内核态 CPU tick；
4. read / pread / write / pwrite、打开关闭文件、截断、预分配以及 fsync / fdatasync 等选定系统调用的 calls、errors 和耗时汇总；
5. Read-family calls、Write-family calls 和 Sync-family calls 三项派生调用总数。

当前报告不计算每次成功提交事务对应的存储读写字节、读写调用比或每次同步操作覆盖的成功提交事务数。

这些数据适合定位 I/O 放大、频繁小写、同步过密、异常错误调用或 CPU/调度压力， 但需要结合缓存、group commit、后台脏页写回和恢复实现进行分析。观测到的同步调用数 不能替代功能阶段的 COMMIT 持久化校验，也不能单独证明或否定数据库正确性。

## 六、优化规范与实现建议

### （一）ACID 优化红线（强制）

本节是成绩有效性的强制规范，不是可选的实现建议。执行计划、索引、缓冲池、并发控制、WAL、checkpoint、恢复、批执行、批量装载、异步 I/O 及网络传输等任何针对性能的改动，都不得改变或绕过 ACID 语义。该要求同时适用于 EXEC_STREAM、PREPARE_SET/EXEC_BATCH、装载、预热、正式测量、诊断与恢复路径，不存在可以降低事务保证的“性能专用路径”。

核心判定原则是可观察等价：在合法请求、并发冲突、业务回滚、连接异常以及强制终止/重启等情形下，启用优化前后的提交结果、可见性、错误与回滚语义、 Wire Protocol 状态以及恢复后数据都必须符合同一事务契约。优化可以改变内部算法、调度和物理访问路径，不得改变对外正确性。合法并发调度可以导致不同的提交次序或冲突受害者，但每一个可观察结果仍必须满足赛题规定的隔离与事务语义；题面明确规定固定中止点和 victim 的 SSI 历史除外（见第三章第（五）节赛题额外协议）。

| ACID 属性 | 本赛题中的强制要求 | 禁止的优化方式（包括但不限于） |
| --- | --- | --- |
| 原子性 Atomicity | 事务的表记录、所有相关索引、计数与关联更新必须整体提交或整体回滚；AUTO_ABORT 失败且连接存在活动事务时，必须在失败响应前完成回滚 | 部分写入后返回成功；只回滚表或只回滚索引；使部分执行或延迟 undo 的未提交更改对外可见 |
| 一致性 Consistency | 每笔成功提交事务都必须保持 SQL 语义、表/索引一致及 TPC-C 关联、计数和金额不变量；查询必须返回真实状态 | 省略某类事务或某个写集；使用过期缓存、近似值、预置结果或针对固定负载的专用条件分支代替正常执行；延后必要的索引维护，导致查询无法观察到正确的成功提交状态 |
| 隔离性 Isolation | 在本说明规定的多客户端并发条件下，执行必须符合赛题隔离语义；未提交更新不得对其他事务可见，且不得产生丢失更新、重复订单号或重复领取 Delivery 等异常 | 取消必要的冲突检测；共享跨事务可变状态以换取吞吐；未经正确验证即允许乐观或 MVCC 事务提交；将冲突、超时或未完成回滚计为成功提交；以单线程/无交错假设替代并发正确性 |
| 持久性 Durability | COMMIT 成功应答前，对应 WAL 记录及其依赖必须已写入并完成可核验的稳定化；遵守 WAL 先行规则；成功提交数据在 SIGKILL 和重启后仍正确可见 | 在稳定化前返回 COMMIT 成功；仅写入操作系统页缓存；等待 checkpoint、正常关闭或后台延迟同步；以同步无关文件或令牌文件替代 WAL 持久化；以“理论持久但不可被本节审计观测”主张免责 |

### （二）通用性与禁止硬编码（强制）

所有优化必须面向由语义定义的一类合法输入，而不是只对某次发布、某组随机数据或排行榜高频执行路径的特定实例成立。判断通用性的基本标准是：在 SQL 与协议契约不变的前提下，改变标识符、SQL 的等价书写、参数和数据值、行数与数据分布、请求顺序、客户端映射、并发调度或故障时点后，优化路径仍能执行真实操作并返回正确结果；优化前置条件不成立时，必须回退到正确的通用路径。

本节所称“等价书写”仅指本说明及协议明确支持的 SQL 语法子集内，空白、关键字大小写、允许的括号和已公开语法形式的等价变化；不据此扩大参赛 SQL 引擎必须支持的语法集合， 也不要求对 JOIN 改写、子查询变换、任意代数等价式或类型转换保持同一优化路径。

这里所称“硬编码”不只包括在源码中写死答案或常量，也包括直接或间接识别测评实例后采用测评专用条件分支。禁止的方式包括但不限于：

1. 匹配表名、列名、文件名、原始 SQL、SQL 哈希、固定 statement_id、参数组合、行数、随机数据特征、环境信息、客户端编号、测评阶段或时间顺序来识别测评请求；
2. 预置或推导应返回的行、计数、聚合值、订单号、事务结果，或依据预期后续请求省略真实的解析、执行、读写、锁、日志、索引维护、回滚或恢复；
3. 只实现已知数据规模、分布、访问序列或故障位置下的快速路径，而对同类合法输入返回错误结果、非真实结果或不具备正确的回退路径；
4. 利用报告中的阶段名、诊断码、表序号、语句序号或进度信息识别测评请求，并据此返回预置答案、跳过真实执行或进入测评专用分支。

正常的 prepared statement 字典、以 SQL 文本或哈希为键的计划缓存、基于 schema 的索引，以及依据统计信息和运行时状态选择执行计划，本身不属于硬编码；但它们只能用于定位和复用执行对象，仍须绑定本次真实参数、访问本次真实数据、正确维护与失效状态，并对所有满足前置条件的输入保持语义等价。statement_id 可用于查找本连接已安装的语句，不得用于识别测评事务后替代其真实执行。

测评的名称、数据、参数、请求顺序、并发交错和故障时点均可能随机化或调整。【审查性红线】一经测评或复核确认以硬编码或测评专用条件分支替代通用实现，按完整性或正确性失败处理，相关性能成绩无效。

### （三）合规的优化边界

下列方向可以使用，但“可以”始终以同时满足上述 ACID 红线和通用性规范为前提：

| 优化方向 | 必须保留的语义 |
| --- | --- |
| 解析/计划缓存、算子优化、向量化、EXEC_BATCH 与聚合网络写 | 只读计划可共享；参数、运行态、事务状态和结果必须正确隔离；批次顺序、事务边界与失败回滚不变 |
| 索引、数据布局、页缓存与查询结果缓存 | 必须遵守事务可见性并在更新、回滚和恢复时正确维护或失效；经事务可见性判断后，通过表扫描与任一索引访问得到的对外结果必须对应同一合法提交状态。允许内部保留历史版本、ghost entry 或待清理项，前提是其不得被错误观察到，且不得导致重复键、错误计数、错误可见性或恢复后不一致 |
| 细粒度锁、分区 latch、乐观并发控制或 MVCC | 必须按赛题隔离语义正确处理读写/写写冲突，提交前完成必要验证；冲突失败时整笔回滚，不得暴露中间状态 |
| group commit、WAL 批量写、异步 I/O | 只有在覆盖该事务 commit record 的稳定化操作完成后，才能向该事务返回成功；异步执行状态不能替代持久化完成；并须同时满足崩溃后可见性要求与第五章第（三）节可核验 WAL 契约 |
| 后台脏页写回、checkpoint、预写页或快速恢复 | 必须遵守 WAL 先行规则；恢复须正确 redo 成功提交事务、清理未成功提交事务，并保持数据页、索引与元数据在对外可观察语义上一致 |
| 批量装载、延后建索引与并行装载 | 必须遵守命令的事务/可见性语义；成功返回时行数、内容、索引和持久化状态必须完整正确 |

### （四）建议的优化顺序（仅供参考）

在满足前述强制规范的前提下，建议参赛队伍按下列优先级组织工作：

1. 正确性基线： 五类事务、业务回滚、崩溃恢复与大规模装载稳定通过后，再进行性能优化。
2. 访问路径： 为客户、订单、未配送订单、明细与库存等高频访问路径配置合适索引，避免不必要的全表扫描与冗余索引维护开销。内部物理计划可自选，但对外 SQL 语义与结果必须正确。
3. 并发控制： 在不降低隔离语义的前提下缩小锁粒度、减少无效等待与死锁；保证 d_next_o_id 与 stock 等热点更新的正确性。
4. 持久化路径： 在同时满足崩溃后可见性与本赛题可核验稳定化契约的前提下，优化日志同步与缓冲池；确保 WAL 先于对应数据页持久化至稳定存储。
5. 测量路径开销： 正式测量期间避免逐事务日志与高频执行路径中的高开销诊断输出，但不得关闭事务 WAL、回滚、冲突检测或必要的索引维护。

【规范要求 / 审查性红线】任何因优化导致的 ACID 违反，或对本说明强制语义的实质性规避，一经测评或复核确认，均按正确性失败或成绩无效处理，不视为可接受的性能权衡；由该路径产生的吞吐、延迟和资源数据不构成有效排名成绩。

## 七、常见问题与排查方向

| 现象 | 可能原因 | 建议排查方向 |
| --- | --- | --- |
| 编译或启动失败 | CMake 目录结构不符合要求、源文件缺失、链接错误或 ELF/RPATH 校验未通过 | 核查构建日志中的第一条 error；确认压缩包根目录包含 CMakeLists.txt 和 src/，且 build/bin/rmdb 为普通 x86-64 ELF 文件 |
| 功能用例失败 | SQL 语义、投影、连接、空结果或事务边界实现错误 | 依次核查报告中的 Failure category、Failed substage、语句序号和进度；使用同类最小 SQL 在本地复现，并核对参赛数据库自己的日志 |
| COUNT(DISTINCT) 失败 | 使用 COUNT(*)、未去重、阈值使用 <=、混入其它仓库数据，或解析器仅接受一种括号形式 | 在联表后去重；使用 s_quantity < threshold；保持订单窗口和仓库隔离；同时支持 COUNT(DISTINCT col) 与 COUNT(DISTINCT (col)) |
| 浮点语义校验未通过 | FLOAT 运算或公开的 binary64-accumulate/one-binary32-round SUM 语义错误、精度过早截断、事务可见性错误或 Wire Protocol 位模式错误 | Payment 逐笔相对更新按报告中的 Before、Bound FLOAT32 amount、Expected、Actual 和 Tolerance 复算；数值同时带 0x????????原始位模式。严格检查为 0 ULP，跨扫描顺序比较可显示 ≤1 ULP，排名量级账本聚合按第三章第（六）节的边界感知规则判定；六位小数仅用于测评程序生成的 SQL 字面量，不是响应文本格式 |
| COMMIT 持久化校验未通过 | COMMIT 在稳定化前返回成功、同步操作未作用于同一 WAL 存储对象、新 segment 缺少父目录同步，或仅发生零字节写入 | 核对每个 ACK 窗口是否先对 db.log、db.log.* 或 wal/** 中的 segment 进行正字节写入，再稳定化同一对象；新建或轮转 segment 还须同步受影响的父目录，可使用 strace 验证 |
| 恢复后数据少于预期 | 成功提交数据未持久化、redo 未执行或持久化顺序错误 | 确认 WAL 在 ACK 前完成稳定化，重启后正确 redo 成功提交事务，并分别核对单线程与多线程恢复用例 |
| 恢复后数据多于预期 | 未成功提交事务未被 undo、redo 不具备幂等性，或索引与表记录不一致 | 恢复时必须撤销未成功提交事务；重复执行恢复不得改变最终结果 |
| 恢复进程存活但验证查询未通过 | open_db、redo、undo 或 catalog 恢复后表不可读，或者查询响应的 META、ROW、终结 frame 不合法 | 核查 Failure category、Failed substage 和可见进度；确认恢复完成后 SELECT 返回 META → ROW* → RESULT_END |
| 装载失败或行数不符 | 大表操作超时、内存不足，或仍假设每个订单固定包含 10 行明细 | 核查 Failure category、Load step、Table ordinal 与 SQL failure / 超时边界；限制缓冲池及事务写集容量并分批 COMMIT；order_line 每个订单动态生成 5～15 行 |
| 装载阶段超时 | 大表装载耗时过长（尤其是 order_line 或 stock），或 COUNT、SUM、范围扫描性能不足 | 核查 Failure category、Timeout boundary、Load step、Table ordinal 和 Operation；应优先核查对应操作及索引 |
| 装载阶段内存不足（OOM） | 缓冲池或事务写集缺少容量上限，或者将整表长期保留在内存中 | 采用有界缓冲、增量脏页写回和淘汰机制；装载完成前不应持有全部 tuple 或索引项 |
| 吞吐量较低且 CPU 利用率不高 | 锁等待、同步操作过于频繁或锁粒度过大导致吞吐受限 | 分析锁等待和同步调用频率；粗粒度锁本身不构成正确性失败，但会显著降低排名 |
| CPU 利用率较高但成功提交数较少 p99 延迟较高 | 冲突重试量过高、全表扫描或死锁处理策略不当长时间持锁、集中脏页写回或偶发全表扫描 | 核查失败与重试统计、热点查询执行计划及锁获取顺序分析慢事务分布和尾延迟形成原因，不应仅依据平均延迟判断 |
| StockLevel 超时或排名无效 | 未原生实现 COUNT(DISTINCT)、语义错误，或未在时限内完成单条聚合 | 使用客户端固定的单条 COUNT(DISTINCT) 联表；内部物理计划可自选，但结果与时限须满足规范 |
| setup / Wire Protocol 校验未通过 | 握手、PREPARE/schema 字典、batch 编码或 AUTO_ABORT 语义错误 | 依据附件 A《RMDB Wire Protocol》核对 8 字节 frame、typed bind、失败计数和短读处理；该现象发生时尚未进入 3 × 150 秒正式测量 |
| Server ERROR response | 测评程序收到完整、合法的 ERROR frame 或 BATCH_RESULT status=ERROR；该状态表示服务端明确返回不可重试的 SQL 失败，不表示连接中断或 frame 解析失败 | 根据 Failed substage、Operation 和 Load step 定位请求，并在本地核查服务端返回的第一条诊断；PREPARE_SET 成功时应返回 PREPARE_OK，普通命令或查询应返回相应成功终结 |
| Unexpected transaction abort | 在必须成功的测活、装载、校验等边界收到了 TRANSACTION_ABORT；该状态表示服务端已经完成回滚，但此处不是测评程序规定的事务重试路径 | 仅对已经完整回滚的可重试事务返回 TRANSACTION_ABORT，不要等待客户端再发 ABORT；解析、语义或不可重试执行错误应返回 ERROR |
| Protocol contract failure（prepared statement） | PREPARE_OK 或 BATCH_RESULT 可解码，但 statement/schema、executed/failed operation、diagnostic 或 result count 不满足状态约束 | 逐项核对附件 A；失败的 AUTO_ABORT batch 不得携带部分查询结果，成功 batch 必须为每个 query 返回且只返回一个正确编号的结果集 |
| Response read timeout / Client/server transport failure | 前者是在截止时间内未收到完整响应，后者是连接在完整终结前关闭、重置或 EOF；两者都不是 ERROR /TRANSACTION_ABORT | 核查连接生命周期、8 字节 header 与完整 payload 的循环读写、响应 flush ，以及每个请求是否具有且仅具有一个完整终结；并发情况下不得提前关闭仍有响应待发送的连接 |
| Transaction isolation violation | SI/SER 配置、MVCC 快照、写写冲突、谓词依赖、SSI 危险结构或依赖清理不符合题面语义 | 按报告中的 Isolation level、Scenario、Session、Scenario step、Operation、Expected terminal 和 Observed terminal 缩小复现范围；会话号和场景步骤均从 1 开始 |
| 本地日志出现 Index entry already exists | d_next_o_id 重复、索引键构造错误，或回滚后仍残留堆记录/索引项 | 确认订单号分配受正确并发控制；核查(w,d,c,o) 索引键，并保证堆与全部二级索引随事务共同回滚 |
| 预热或测量阶段出现 Client/server transport failure | 并发事务发生错误、rmdb 进程退出或连接提前关闭 | 核查 Failure category、Failed substage、Transport event 和 Operation；先使用单连接复现，再逐步增加并发连接数 |
| 唯一约束错误（性能负载） | d_next_o_id 并发竞争、键冲突或 ABORT 后存在索引项残留 | 在事务内原子分配订单号并实施正确的并发控制；冲突必须按事务语义回滚，不得通过主动断开连接处理 |
| Wire Protocol 校验未通过 | 仍使用旧 NUL 协议、8 字节 frame 格式错误、META/ROW 错误或 batch schema/结果不一致 | 精确回送正式握手；循环读写 header 和 payload；区分 EXEC_STREAM 与单 frame BATCH_RESULT |
| Consistency mismatch | 并发更新丢失、事务部分提交、回滚残留或恢复结果不一致 | 根据 Failed substage 区分强制终止前与恢复后校验；在本地按第五章公开不变量逐项核对，优先检查首个可复现偏差 |
| Payment 累计金额不一致 | w_ytd、d_ytd 或 c_ytd_payment 未更新，或者并发更新丢失 | 每次成功提交的 Payment 必须同步更新三项累计金额并插入一条 history 记录 |
| Delivery 相关累计量不一致 | 未领取最早未配送订单，或未更新客户余额及 c_delivery_cnt | new_orders 删除、order_line 配送状态和 customer 更新必须属于同一事务 |
| 正式测量期间 rmdb 进程退出 | 程序异常、内存不足或断言失败 | 根据公开的 Failure category、Failed substage 和进程边界定位；完整服务日志不在学生报告中展示，应先在本地复现后再进行并发验证 |
| 读写诊断 WARN | strace 权限不足或数据采集失败 | 该项不计分，Score 和排行榜结果不变；如需核查测评环境，可联系赛事技术支持 |

### 报告信息核查顺序

1. 首先定位最早未通过的阶段（编译 → 功能正确性/COMMIT 持久化/崩溃恢复 → 装载 → 排名负载 →在线一致性 → 恢复后校验 → 读写诊断），不应从后续派生现象反推原因。
2. 结构化字段按 Failure category → Failed substage → Key fields 阅读；诊断只展示实测事实与已确认的观察，不展示未经证实的原因推断。未通过项始终展开，已通过项统一放在默认折叠区。
3. 可配置隔离级别失败会公开 Isolation level、场景族、会话号、场景内步骤、操作类型以及期望/实际终结。它们用于区分配置持久性、快照可见性、活跃/陈旧写冲突、谓词依赖、写偏序和依赖清理等边界；隐藏 SQL、表名、行值和完整调度仍只保留在教师证据中。
4. TPC-C 性能门禁会公开具体检查类别及必要聚合量：五类事务提交数、Delivery 实际处理行数、完成事务样本数、已覆盖/最低要求仓库数、热点仓覆盖数，以及该样本量下完整热点门禁是否生效。报告会明确区分“事务族未完成”“Delivery 始终为空”“单轮覆盖不足”和“三轮合并覆盖不足”，不再统一显示为泛化的 benchmark contract 失败。
5. 功能或恢复语义不一致时，优先查看语句序号、语句进度和失败阶段；装载失败时查看 Load step、Table ordinal、Operation 与对应的超时、传输或 SQL 边界。
6. 一致性失败公开脱敏后的校验范围、允许列表检查名、期望值、实际值和 tolerance （严格 FLOAT32 为十六进制 bit pattern、0 ULP）；不公开 SQL、运行时标识或记录键。应依据第五章的公开事务语义和不变量，在本地构造数据逐项核对。
7. 报告聚焦首次确认的失败边界，不承诺公开生成 SQL、答案或后续校验结果；应优先修正首个可在本地复现的问题，再重新执行完整回归。

应优先定位首次失败点；后续异常可能是由该失败引起的派生结果。

## 八、参赛提交前自检清单

### （一）正确性

- 所有优化路径在 EXEC_STREAM、EXEC_BATCH 及各测评阶段中均保持 ACID，不设置降低语义要求的专用分支
- 五类事务在空结果、冲突与边界条件下行为正确
- NewOrder 遇无效商品时整笔回滚
- 提交、回滚和恢复后，表扫描与任一索引在可见性判断后对应同一合法提交状态；内部历史版本/待清理项不可被错误观察
- o_ol_cnt 与明细行数始终一致
- Stock 更新满足并发安全要求
- Delivery 按最早未配送订单处理
- StockLevel 去重语义正确；单条 COUNT(DISTINCT) 在时限内返回正确类型化结果，且不依赖客户端后处理
- Wire Protocol 能处理握手、8 字节 frame、短读/短写、INT32/FLOAT32/CHAR 与空结果；本届正式负载不要求 SQL NULL
- EXEC_STREAM 流式结果、PREPARE_SET 原子字典安装、EXEC_BATCH typed bind/packed result 均正确
- AUTO_ABORT 在失败响应前完成回滚，TRANSACTION_ABORT 后不等待第二次 ABORT

### （二）通用性与反硬编码

- 更换表名、列名、文件名、本说明界定的 SQL 等价写法、statement_id、参数值、数据规模与分布后，同类合法输入仍能正确执行
- 改变请求顺序、客户端映射、并发交错、测评阶段或故障时点后，不会进入测评专用条件分支
- 计划或结果缓存始终绑定真实参数并访问真实数据库状态，不含预置答案、固定计数或跳过语义执行的分支
- 专用快速路径具有明确的语义前置条件、完整的状态维护与失效机制，以及正确的通用回退路径
- 不以固定客户端数、固定连接模式或“请求不会交错”作为正确性前提

### （三）并发与性能

- 在 32 客户端并发负载下隔离语义与冲突处理正确（锁粒度可影响排名，但不得降低正确性）
- 细粒度锁、乐观执行或 MVCC 优化不会造成脏读、丢失更新、重复取号或重复配送
- 五类事务均能持续有效提交
- 每个正式测量轮中五类事务均能至少成功提交一笔
- 每个正式测量轮至少有一笔 Delivery 实际处理排队订单
- 完成样本达到 400 笔时，每轮至少覆盖 45 个归属仓库及全部热点仓，三轮合并覆盖 50 个仓库；低样本按规则缩放
- 不存在过量死锁重试或无界重试
- 高频访问路径具备合理索引
- 正式测量期间无逐事务级冗余日志
- 多窗口结果稳定，而非单次偶然峰值

### （四）持久化与恢复

- 强制终止后成功提交数据仍然存在
- 未成功提交数据不可见
- 每个 COMMIT 成功应答前，本事务的 WAL 新写入已被本赛题可核验的稳定化操作覆盖
- group commit 或异步 I/O 不会在对应稳定化完成前返回成功
- WAL 命名空间与 syncfs 路径边界符合第五章第（三）节自动审计契约
- 不以“理论持久但不可被审计观测”主张免责
- 多次恢复结果稳定（建议本地回归；非单个用例内重复恢复门禁）
- WAL 与数据页的稳定存储顺序正确
- 大规模装载后重启仍通过行数校验

### （五）指标表述

- 吞吐量统一表述为 NewOrder 成功提交速率（笔/分钟）
- 区分成功提交、业务预期回滚与失败放弃
- 关注成功提交事务的端到端 p99，而非仅使用平均值

## 九、结语

本决赛测评综合考查事务语义、并发控制、日志与崩溃恢复、存储可靠性以及 TPC-C 持续高负载下的稳定性与吞吐能力。

组委会建议参赛队伍：

1. 把 ACID 作为所有优化的硬性前提，在正确性与可恢复性成立后再追求吞吐；
2. 确保优化面向一类合法输入，在随机名称、数据、调度和故障条件下仍然正确，不以硬编码答案或测评专用分支换取吞吐；
3. 依据执行计划、锁等待、日志与缓冲池行为定位瓶颈；
4. 每次关键修改后，对成功提交、业务预期回滚、并发冲突和强制终止恢复进行回归；
5. 以多窗口中位吞吐与 p99 延迟作为优化目标，避免追求不可复现的峰值。

ACID 与通用性决定优化是否合法；正确性决定成绩是否有效；稳定性决定成绩能否复现；合规的性能优化决定最终排名。自动测试通过不是规避本说明强制条款的依据。

*本文档最终解释权归赛项组委会所有。 时间参数、阈值和环境配置以届时生效版本及对应组委会公告为准。

## 附件 A：RMDB Wire Protocol

本附件是参赛数据库服务端与测评系统之间的公开字节级协议，属于主文档的规范性组成部分。正式协议保留流式 SQL 通道 EXEC_STREAM，并增加连接级语句字典 PREPARE_SET 与依赖阶段批执行 EXEC_BATCH。 本协议与历史协议不兼容。所有多字节整数均为大端序。除明确说明外，TCP 分片不改变协议语义。 本附件所称“客户端”是指测评系统的协议客户端，“服务器”是指参赛数据库服务端。双方必须循环读写，直到完整 header 和 payload 均传输完毕。

本赛题中的 SET TRANSACTION ISOLATION LEVEL ... 是连接会话配置：成功设置后持续作用于该连接后续新开启的事务，不是只消费一次的 next-transaction 设置。功能用例会在连接建立后、 首个 BEGIN 前设置一次，不会在活动事务内重新设置。

功能测评会精确发送并检查以下两种配置：

```text
SET TRANSACTION ISOLATION LEVEL SNAPSHOT ISOLATION;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

两条语句都应返回 COMMAND_OK。除语法与配置测试外，同一语义测试点中的多个连接只使用同一种隔离级别；TPC-C 排名连接固定使用 SNAPSHOT ISOLATION。

本协议在保持大结果流式返回能力的同时，减少排名事务中逐条短 SQL 引起的网络往返、 SQL 文本传输、重复解析和逐条 DML ACK 开销。

### 1. 连接与并发模型

TCP 连接建立后，客户端先发送 8 字节：

| offset | size | value |
| --- | --- | --- |
| 0 | 4 | ASCII "RMDB" (52 4d 44 42) |
| 4 | 2 | major = 3 |
| 6 | 2 | minor = 0 |

服务器必须原样回送这 8 字节，然后才能读取第一个 frame。握手不被支持时应关闭连接， 不得把握手字节交给 SQL parser。

一次连接可顺序处理多个请求，但同一连接在任一时刻只有一个 outstanding request：客户端收到当前请求的完整响应后才会发送下一个请求。协议不要求 requestid、乱序响应、 pipeline 或多路复用；并发由多个 TCP 连接提供。服务器不得在同一连接上自行重排两个 请求，EXEC_BATCH 内的 operation 也必须严格按编码顺序执行。

### 2. 通用 frame

握手完成后，客户端请求和服务器响应都使用相同的 8 字节 header：

```text
u32 payload_bytes       // 不含本 header
u8  tag
u8  flags
u16 reserved            // 必须为 0
u8  payload[payload_bytes]
```

单个请求或响应 payload 上限为 1 MiB。服务器响应的 flags 与 reserved 必须均 为 0。客户端请求中，只有 EXEC_BATCH 使用已定义的 flag；其余请求的 flags 必须 为 0。未知 tag、未知 flag、非零 reserved、截断字段或 payload 尾随未解释字节均为 协议错误。

| 方向 | tag | 名称 | 用途 |
| --- | --- | --- | --- |
| C → S | 0x20 | EXEC_STREAM | 执行一条普通 SQL，结果按 frame 流式返回 |
| C → S | 0x21 | PREPARE_SET | 安装或替换本连接的有界语句字典 |
| C → S | 0x22 | EXEC_BATCH | 顺序执行一组已准备 operation，返回一个压缩结果 |
| S → C | 0x01 | META | EXEC_STREAM 查询列定义 |
| S → C | 0x02 | ROW | EXEC_STREAM 的一行类型化数据 |
| S → C | 0x10 | COMMAND_OK | EXEC_STREAM 非查询成功 |
| S → C | 0x11 | RESULT_END | EXEC_STREAM 查询成功终结 |
| S → C | 0x12 | TRANSACTION_ABORT | EXEC_STREAM 事务已被服务器回滚 |
| S → C | 0x13 | ERROR | 请求失败诊断 |
| S → C | 0x14 | PREPARE_OK | 语句字典安装成功及查询 schema 字典 |
| S → C | 0x15 | BATCH_RESULT | EXEC_BATCH 的唯一压缩响应 |

### 3. 公共类型编码

SQL typetag：

```text
0x01 = INT32
0x02 = FLOAT32
0x03 = CHAR
```

列定义编码为：

```text
u16 name_bytes           // 必须 > 0
u8  name[name_bytes]     // UTF-8，通常为列名或 AS alias
u8  sql_type
```

一个 cell 的类型由 schema 或 prepared parameter 声明确定，wire 中不重复发送 type：

```text
u8 present               // 0 = NULL；1 = 后接非 NULL 值
if present == 1:
INT32:   i32          // two's-complement, big-endian
FLOAT32: u32          // IEEE-754 binary32 原始 bit pattern, big-endian
CHAR:    u32 byte_count + u8 value[byte_count]
```

合法 present 只有 0 和 1；NULL 后没有值字节。CHAR 发送逻辑字符串的原始字节， 不发送页内定长 padding，也不追加 NUL。FLOAT 不经十进制文本格式化。

present=0 是协议层保留编码，不代表本届学生 SQL 引擎必须实现 NULL。正式 TPC-C 兼容数据和事务不写入或绑定 SQL NULL：未配送的整数列使用 0，未配送的字符时间戳使用空字符串。聚合空集可按测评 SQL 约定返回空结果或整数 0。

#### 3.1 FLOAT 运算、聚合与判定

- FLOAT 存储、literal 与 FLOAT32 bind 均采用 IEEE-754 binary32， round-to-nearest,ties-to-even；受检结果必须有限；
- FLOAT 相对加减的每次更新均在 binary32 中执行并舍入一次；
- SUM(FLOAT) 将已存储的 binary32 输入精确扩展为 binary64，在 binary64 中累加， 最后舍入一次为 binary32，并以 FLOAT32 cell 返回；本协议不规定合法 binary64 累加顺序；
- +0 与 -0 在数值一致性比较中等价；
- 单笔事务相对更新、单个订单的 SUM 与整数量累计采用 0 ULP；
- 排名量级的 SUM(h_amount) 与新订单 SUM(ol_amount) 账本核对采用主文档规定的边界感知判定；崩溃前后七项聚合基线中，w_ytd、d_ytd、s_ytd 采用 0 ULP，其余四项因扫描顺序不受协议约束而采用 ≤1 ULP。

### 4. EXEC_STREAM：保留的通用流式路径

#### 4.1 请求

```text
EXEC_STREAM 使用 tag 0x20、flags 0，payload 是一条非空 UTF-8 SQL：
u8 sql[payload_bytes]    // 不含 NUL；总长不超过 1 MiB
```

它用于功能测试、恢复测试、DDL、装载以及可能产生大结果的查询。服务器处理完该请求的 唯一终结 frame 后，继续读取下一请求。

#### 4.2 查询结果

成功查询的严格顺序是：一个 META、零个或多个 ROW、一个 RESULT_END。

META payload：

```text
u16 column_count         // 必须 > 0
repeat column_count times:
column_definition
```

每个 ROW payload 按 META 列顺序串联 cell，不额外携带列数或行长度：

```text
repeat column_count times:
cell
```

RESULT_END payload 是一个 u64 row_count，必须等于实际发送的 ROW frame 数。 不得重复 META，不得在 META 前发送 ROW，不得在终结 frame 后继续发送本请求数据。

#### 4.3 非查询、错误与回滚

成功的 DDL、DML、LOAD 和事务控制语句只返回一个 payload 为空的 COMMAND_OK；查询 只能以 RESULT_END 成功，非查询只能以 COMMAND_OK 成功，二者不可互换。

TRANSACTION_ABORT 和 ERROR 的 payload 都是至多 64 KiB 的 UTF-8 诊断。服务器 主动回滚当前事务时使用 TRANSACTION_ABORT：发送前必须已经原子回滚并结束事务； 客户端收到后直接重试，不会再发送第二次 ABORT。普通解析、语义或执行错误使用 ERROR。流式结果中途失败时，客户端丢弃已收到的 META/ROW。

### 5. PREPARE_SET：连接级语句与 schema 字典

排名连接先通过 EXEC_STREAM 执行 SET TRANSACTION ISOLATION LEVEL SNAPSHOT ISOLATION; 并收到 COMMAND_OK， 再在开始计时前发送一次 PREPARE_SET。tag 为 0x21，flags 为 0。每个连接独立维护字典；statementid 不是跨连接全局对象。语句数必须在 1..=256，id 必须非零 且互不重复。

请求 payload：

```text
u16 statement_count
repeat statement_count times, in request order:
u16 statement_id
u8  result_kind       // 0 = command；1 = query
u16 parameter_count
repeat parameter_count times:
u8 parameter_sql_type
u32 sql_bytes
u8  sql[sql_bytes]
```

SQL 使用 $1、$2、… 表示 typed parameter。ordinal 从 1 开始，必须形成 1..=parameter_count 的稠密集合；同一参数可出现多次。单引号字符串内部的 $n 只是文本，不是 marker。服务器应在安装字典时完成解析、绑定与可复用计划准备，不应在 每次 EXEC_BATCH 中重新解析完整 SQL。参数必须按声明类型绑定；实现即使内部生成 literal，也必须保证 CHAR、NULL 和 FLOAT 与 typed bind 等价，不能进行未经转义的 字符串拼接。

成功时服务器只返回一个 PREPARE_OK（tag 0x14）：

```text
u16 statement_count                     // 必须等于请求值
repeat statement_count times, in request order:
u16 statement_id                     // 必须逐项等于请求 id
u16 column_count
repeat column_count times:
column_definition
```

command 的 column_count 必须为 0；query 的列数、顺序和 SQL type 必须与该 SQL 的 实际投影 schema 精确一致。测评程序会按已知排名模板逐列核对类型，不接受仅返回一个占位列、遗漏未由测评程序读取的投影列或把数值列伪装为 CHAR。查询 schema 只在这里传输 一次，后续 BATCH_RESULT 不再重复列名和类型。整个字典验证成功后才原子替换旧字典； 失败时返回 ERROR，不得留下部分安装的字典状态。

### 6. EXEC_BATCH：依赖阶段批执行

#### 6.1 请求

```text
EXEC_BATCH tag 为 0x22，flags 必须为 0x01：
flags bit 0 = AUTO_ABORT
```

请求包含 1..=256 个 operation：

```text
u16 operation_count
repeat operation_count times:
u16 statement_id
repeat prepared.parameter_count times:
typed cell value
```

operation 不发送参数数量和参数类型；它们由当前连接的 prepared 字典确定。服务器必须 严格顺序执行 operation：后面的语句可以依赖前面语句取得的锁或产生的写入，但不能直接引用前面查询返回给客户端的值。需要客户端读取查询结果才能生成后续参数时，客户 端会结束当前 batch，并发送下一个依赖阶段 batch。

AUTO_ABORT 是硬性原子性约束：任一 operation 解析、绑定或执行失败时，如果连接上存在活动事务，服务器必须在发送失败响应前完成回滚并结束事务。客户端不得依赖失败 batch 的部分结果，也不会为了可重试冲突补发第二次 ABORT。

#### 6.2 唯一响应 BATCH_RESULT

成功接收并执行 batch 后，服务器只返回一个 tag 0x15 frame：

```text
u16 executed_operations
u8  status
u16 failed_operation
u32 diagnostic_bytes
u8  diagnostic[diagnostic_bytes]         // UTF-8，最多 64 KiB
u16 result_count
repeat result_count times:
u16 operation_index                  // 从 0 开始，严格递增
u32 row_count
repeat row_count times:
repeat prepared_query.column_count times:
typed cell value
```

query 的 schema 来自 PREPARE_OK；每行没有独立长度，command 不出现在结果列表中。排名查询结果有界，完整 BATCH_RESULT 必须放入一个不超过 1 MiB 的 frame；可能产生 大结果的 SQL 必须走 EXEC_STREAM。

status 与字段约束如下：

| status | 名称 | 严格约束 |
| --- | --- | --- |
| 0 | OK | executed_operations ==operation_count；failed_operation ==0xffff；诊断为空；每个 query operation 恰有一个结果，command 没有结果 |
| 1 | TRANSACTION_ABORT | executed_operations <operation_count；failed_operation ==executed_operations；result_count== 0；事务已经回滚；客户端可重试 |
| 2 | ERROR | 与 status 1 的计数约束相同；result_count == 0；活动事务已经回滚；客户端将其视为不可恢复的实现/协议失败 |

这里 executed_operations 表示触发错误的 operation 之前已经尝试执行、但其效果现已随活动事务原子回滚的 operation 数量；该计数只描述失败位置和执行进度，不表示前面的修改仍然生效。failed_operation 是从 0 开始计数的触发失败位置，失败 operation 本身 不计入 executed_operations。失败响应不得携带前面 query 的部分结果。若请求在执行 任何 operation 前即无法解码，服务器也可返回顶层 ERROR；在 AUTO_ABORT 下仍必须 先清理已有活动事务。

### 7. 排名事务的批次边界

测评程序按实际数据依赖划分 batch，不并行执行存在依赖关系的 SQL，也不要求服务器支持 pipeline。无冲突、无重试的一次事务采用以下往返数：

| 事务 | 依赖阶段 | batch 往返数 |
| --- | --- | --- |
| NewOrder | BEGIN/基础行及按 (供货仓, 商品) 升序去重锁定全部库存行/按原明细顺序读取 →写入全部有效明细/COMMIT；无效商品路径写入此前有效明细后 ABORT | 2 |
| Payment | BEGIN/读取与更新基础行 →更新客户/History/COMMIT | 2 |
| OrderStatus | BEGIN/客户 → 最近订单 →明细/COMMIT | 3 |
| Delivery | BEGIN/10 个 MIN →对非空区锁定、确认领取并读取明细及 SUM(ol_amount) → 以该 SUM 更新客户余额、删除队列项及完成其余业务更新/COMMIT；全空时直接 COMMIT | 2～3 |
| StockLevel | BEGIN/next order → DISTINCT count/COMMIT | 2 |

按 45/43/4/4/4 混合比例，理想无重试路径的加权平均约为 2.08 次 batch RTT/事务。 单笔 Delivery 在十个分区均无待配送订单时可以正常提交；但每个正式测量窗口必须至少有 一笔 Delivery 实际处理排队订单，持续将非空队列错误报告为空不能通过性能正确性门禁。 隔离级别设置和 PREPARE_SET 都在每个排名连接同步开始测量前完成，不计入测量窗口。 功能、恢复、装载和大查询仍使用 EXEC_STREAM，不会被强制缓冲成一个 batch frame。

### 8. 状态机与实现核查表

- header、payload 和 socket write 均使用 read_exact/write_all 等价循环；不得假定 一次 recv 或 send 得到完整字段。
- handshake 后只读取 8 字节 frame header；frame length 不含 header。
- 同一连接一次只处理一个请求；完成唯一响应后再读取下一请求。
- EXEC_STREAM 查询发送 META → ROW* → RESULT_END，非查询只发 COMMAND_OK。
- PREPARE 成功前不得替换旧字典；可缓存 parser/plan 和 query schema。
- batch 参数按 prepared 类型解码，operation 严格顺序执行；成功时不发送逐条 DML ACK。
- 性能关键路径复用有界 buffer；可使用 writev/sendmsg 一次发送 header+payload，减少复制和逐 operation socket flush，但仍须正确处理 partial write。
- AUTO_ABORT 失败响应发出前已经完成回滚；TRANSACTION_ABORT 后不等待第二次 ABORT。
- FLOAT 按 binary32 位模式传输；CHAR 使用实际长度；正式负载使用公开哨兵而不要求 SQL NULL。
- 每个 frame 与诊断均须先校验长度再分配内存；拒绝未知 tag、flag、type 和尾随字节。
- 不实现或发送 SET OUTPUT_FILE OFF/ON；它不属于本测评协议。
